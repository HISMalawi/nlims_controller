3 · Modelo de dados

3.1 Dicionário — propriedade do nacional

Entidades: departments, specimen_types, test_types, indicators, indicator_ranges, test_panels, organisms, drugs, mais as tabelas de ligação (teste↔espécime, teste↔indicador, teste↔organismo, painel↔teste, organismo↔fármaco).

Todos os registos do dicionário partilham a mesma espinha:

uuid
UUID v4, imutável, chave usada em toda a rede
national_code
Código legível e estável, MOZ-TT-0042; é o que aparece nos formulários e nas integrações
status
draft · active · retired
revision
Inteiro global monotónico atribuído no commit; é o cursor de replicação
loinc_code
Opcional, para interoperabilidade externa
moh_code
Opcional, código do MISAU
deleted_at
Nunca se apaga um item que já saiu; marca-se

Ponto técnico decidido em S3

O cursor não pode ser updated_at. Duas transacções concorrentes podem gravar updated_at por ordem diferente daquela em que se tornam visíveis — o nó local avança o cursor e perde permanentemente a alteração mais lenta. O cursor é uma sequência revision atribuída no momento do commit, e o teste de concorrência do passo S3 existe precisamente para provar que não há lacunas.

Como a distribuição é por delta contínuo e não por versões publicadas, o controlo de qualidade passa a estar no estado: uma edição começa sempre em draft e só entra no delta quando alguém a promove a active. A promoção fica auditada com autor e data.

Mapeamentos externos

Cada EMR e cada instalação do SISLAB tem os seus próprios códigos herdados. Em vez de os enfiar no dicionário, vivem numa tabela external_mappings (system, api_client_uuid, entity_type, entity_uuid, external_code, external_name). Substitui o name_mappings actual, que só sabia mapear texto para texto.

Os *_sync_trackers actuais — quatro tabelas com semânticas ligeiramente diferentes — desaparecem, todos substituídos pelo sync_outbox. Um resultado corrigido não sobrescreve o anterior: cria uma nova linha e marca a antiga com replaced_by_uuid, porque o nacional já pode ter distribuído o valor errado.

3.3 Tracking number

Formato MZ-<facility_code>-<yyddd>-<seq>, por exemplo MZ-HCM-26229-0417: prefixo do país, código da unidade que colhe, ano e dia do ano, sequência diária. Gerado sempre pelo nó local, com unicidade garantida por índice único e não por leitura da última linha — o modo actual, com TrackingNumberTrail.last, colide sob concorrência.

4 · Autenticação por API key

Sai o par token + appuuid com expiração e renovação. Entra uma chave por cliente, guardada em hash, com scopes e sem prazo curto. 

Authorization: Bearer ssk_prod_a1b2c3d4_9fK2mZq7XvR4tLpN8sJdW3yH6bC1
                      │    │    │        └─ segredo (32 chars, só existe no cliente)
                      │    │    └────────── prefixo público, indexado, lookup O(1)
                      │    └─────────────── ambiente: prod | staging | dev
                      └──────────────────── sislab sync key

O segredo é guardado como SHA-256 e comparado em tempo constante. O prefixo é indexado para evitar percorrer todas as chaves. A chave transporta consigo o facility_code e o lab_code do cliente — um pedido que tente actuar sobre outra facility recebe 403, mesmo que a chave seja válida.

Scopes
ScopePermitePerfil típico
orders:writeCriar pedidos de exameEMR
orders:readConsultar pedidos e estadosEMR, SISLAB
results:readLer e confirmar recepção de resultadosEMR
results:writePublicar estados e resultadosSISLAB
referrals:writeReferir, receber e rejeitar amostrasSISLAB
dictionary:readPuxar o dicionárioEMR, SISLAB, nó local
dictionary:writeEditar o dicionárioUI do nacional
sync:pushEnviar lotes de eventosNó local
sync:pullPuxar amostras referidas e resultados de foraNó local

Envelope e erros

Todas as respostas usam a mesma forma, e os erros têm código estável — a mensagem é para humanos, o código é para máquinas.

{
  "data":   { "tracking_number": "MZ-HCM-26229-0417", "status": "requested" },
  "meta":   { "next_cursor": "1284471", "has_more": false },
  "errors": []
}

{
  "data": null,
  "errors": [
    { "code": "unknown_test_type", "message": "Teste MOZ-TT-9999 não existe no dicionário", "field": "tests[0].test_type" }
  ]
}
  • 401 unauthenticated — chave em falta, malformada, expirada ou revogada
  • 403 insufficient_scope · 403 facility_mismatch
  • 409 conflict — pedido já reclamado por outro laboratório, ou tracking number já existente
  • 422 unprocessable — validação de domínio, sempre com field
  • 429 rate_limited — com Retry-After

Todos os POST que criam recursos exigem Idempotency-Key. Uma repetição com a mesma chave devolve a resposta original, com o mesmo estado HTTP — indispensável quando a rede cai a meio e o EMR reenvia.

O EMR não envia tracking number. Envia national_code (ou uuid) dos itens do dicionário — nunca nomes livres. Um código desconhecido devolve 422 nomeando o item, o que torna óbvio que o EMR está com o dicionário desactualizado.

Ciclo de vida do pedido

requested ──→ accepted ──→ specimen_collected ──→ in_progress ──→ completed
    │             │                                 ↑    │
    │             ├─────────────────────────────────┘    └──→ referred_out ──→ completed
    │             └──────────→ rejected
    └──→ cancelled

specimen_collected é opcional. Na maior parte das amostras o tubo foi colhido na enfermaria e chegou com o pedido: o laboratório que a recebe não tem colheita nenhuma para registar, e passa de accepted directamente a in_progress. Quem colhe continua a registá-lo — e, para esses, continua a ter de vir antes do trabalho.

Publicar resultados

POST /api/v3/lab/orders/MZ-HCM-26257-0031/results

{
  "results": [
    { "test_type": { "national_code": "MOZ-TT-0042" },
      "indicator": { "national_code": "MOZ-TI-0311" },
      "value": "12.4", "unit": "g/dL",

final: false permite publicar resultados à medida que saem. Reenviar o mesmo indicador cria uma nova linha e marca a anterior como substituída — o nacional recebe as duas e sabe qual vale. O lab_code da chave tem de coincidir com o do pedido; caso contrário, 403 facility_mismatch.

{ "data": { "accepted": ["a1f0…", "b7c3…"], "rejected": [] }, "errors": [] }

Garantias

  • At-least-once com idempotência. O evento é escrito no outbox na mesma transacção que altera o domínio. O nacional aceita cada event_uuid uma só vez; reenviar é seguro.
  • Ordem por agregado. O sequence é por aggregate_uuid. Um evento fora de ordem fica em espera até chegar o anterior, em vez de ser aplicado errado.
  • Nada se apaga. O outbox marca delivered_at; falhas guardam last_error e contam attempts, com backoff exponencial e reprocessamento manual pela UI.
  • Rejeição explícita. Um evento rejeitado (por exemplo, refere um teste que não existe no dicionário nacional) volta com código e mensagem, e fica visível na fila de sincronização em vez de desaparecer nos logs.

Tipos de evento: patient.upserted, order.created, order.status_changed, order.test_added, test.status_changed, test.result_recorded, specimen.rejected, referral.dispatched, referral.received, referral.rejected.

8 · Referenciamento de amostras

Três códigos acompanham a amostra do início ao fim: sending_facility_code (quem colhe e envia), receiving_lab_code (o laboratório que executa) e lab_code (a secção dentro desse laboratório). O tracking number nunca muda, mesmo quando a amostra atravessa duas instituições.

Percurso de uma amostra referida
#OndeAconteceRegisto
1Lab ANão executa o teste; cria a referência para o lab Breferral.dispatched, pedido passa a referred_out
2Nó local AEmpurra o eventoOutbox → nacional
3NacionalIndexa e encaminha para o nó de BDisponível em /sync/inbound
4Nó local BPuxa e cria o pedido como referred_inAparece em pending-orders com a origem
5Lab BRecebe fisicamente a amostra — ou rejeita-areferral.received ou referral.rejected
6Lab BExecuta e publica o resultadotest.result_recorded
7Nacional → nó AResultado volta à unidade de origem/sync/inbound
8EMR de APuxa o resultado com o mesmo tracking number/results?since=

A tabela referrals guarda from_facility_code, from_lab_code, to_lab_code, state, dispatched_at, received_at, rejected_at, rejection_reason, courier e remarks. A diferença entre dispatched_at e received_at é a métrica de transporte que hoje ninguém consegue medir.

API EMR ↔ nó local

S13

O nó é a unidade sanitária

30 ago

Corrigir a identidade do nó. S6 assumiu que uma instalação servia um laboratório; não serve — uma instância do mLab serve todos os laboratórios da unidade, cada um com o seu código, e todos chegam à rede pelo mesmo nó. A unidade sanitária passa a ser o que um nó é, e os laboratórios passam a viver por baixo dela.

Feito quando uma instalação é identificada por SISLAB_SYNC_FACILITY_CODE, um laboratório desconhecido que envia a primeira amostra é registado sem recusar nada e recebe código nacional pela sincronização de rotina, um pedido do EMR chega à unidade sem laboratório e ganha-o na reclamação, e uma amostra passada entre duas bancadas da mesma unidade resolve-se no nó sem ir à capital.

  • Entidade de dicionário facilities, propriedade do nó nacional, no mesmo feed e na mesma sequência de revisões; labs aponta para ela
  • SISLAB_SYNC_FACILITY_CODE é a identidade; SISLAB_SYNC_LAB_CODE é recusada com a indicação da renomeação
  • Bloco lab no pedido: código desconhecido é registado na mesma transacção, com source_code e sem código nacional
  • Evento lab.registered na outbox existente; o nó nacional aceita e publica sempre, e devolve o código nacional pelo feed do dicionário
  • orders.receiving_facility_code obrigatório, receiving_lab_code facultativo; a reclamação atribui a bancada
  • Encaminhamento por unidade sanitária: Sync::Routing, /sync/inbound, authorize_node! e o heartbeat
  • Referenciamento entre bancadas da mesma unidade resolve-se no nó; sobe como evento, não é encaminhado de volta
  • specimen_collected facultativo: uma bancada que não colheu passa de accepted a in_progress
  • Contrato, colecção Postman, gem de referência e README acompanham

  • feat(identity): a node is a health facility, not a laboratory
  • feat(intake): register a laboratory the first time it sends a sample
  • feat(sync): route by health facility and settle internal handovers locally
  • docs(api): describe the facility register, and teach the client gem about it
  • feat(lifecycle): start work on a sample the ward already collected

12 · Pressupostos e âmbito

Pressupostos assumidos

  • Ruby 3.3+, Rails 8, MySQL 8, Redis e Sidekiq mantidos como base técnica
  • O identificador do doente é o NID de Moçambique
  • O trabalho decorre na branch v2 e é integrado em main na entrega; a numeração continua a linhagem de tags do repositório, que já vai em v3.2.8, pelo que a primeira versão do SISLAB Sync é a v4.0.0

  • Não há migração de dados históricos, porque o NLIMS não está em produção
  • TLS terminado por um proxy à frente da aplicação, em ambos os modos
